基础验证 —— 让 AI 跑出第一个 3D 模型
05-08

目标

在 RTX 3060 Laptop (6GB VRAM) 上跑通 TripoSR 模型，从一张照片生成带顶点色的 3D 网格。 这是整个项目的可行性验证 —— 如果 AI 无法在消费级硬件上生成可用的 3D 模型，后续所有工作都没有意义。

关键里程碑

TripoSR 模型加载成功VRAM 占用 ~3.5GB，6GB 显卡完全够用
首张图片推理通过DINO ViT → Transformer → NeRF → Marching Cubes，~2s 出网格
rembg 背景去除集成GPU 加速模式，前景裁切 + 居中，输出质量显著提升
torchmcubes → skimage 迁移原库仅支持 Linux，替换为跨平台的 marching_cubes 实现
HuggingFace 模型下载配置 hf-mirror.com 镜像加速国内下载

踩坑：torchmcubes Windows 不兼容

TripoSR 官方代码使用 torchmcubes 进行 Marching Cubes 提取，但该库的 CUDA kernel 只为 Linux 编译。 在 Windows 上直接 ModuleNotFoundError。 解决方案：用 skimage.measure.marching_cubes 替换，虽然走 CPU 但速度可接受（~0.5s）， 且零依赖问题。

经验：先跑通再优化

第一个版本的 image-to-3d.py 只有 50 行：加载模型 → 推理 → 导出。 不纠结参数抽象、不搞配置文件、不过早优化。跑通后才有资格谈架构。 这条原则贯穿了整个项目 —— 每个阶段都先用最简方式验证核心假设。

1
管线完善 —— 从网格到可打印 STL 的完整链路
05-09 ~ 05-10

目标

AI 生成的原始网格不能直接打印 —— 有破洞、非流形边、重复面。需要修复、缩放、落地。 同时补齐浮雕/夜灯生成、六视图渲染、端到端编排等能力，形成完整的 CLI 工具链。

新增脚本

mesh-repair.py Watertight 修复管线：去重 → 去退化 → pymeshfix 填洞 → 缩放 → 落地 → 导出 STL
mesh-to-views.py 6 正交视图渲染（前/后/左/右/上/下），pyrender 离屏渲染，3×2 网格拼图
pipeline.py 端到端编排器：image → 3D → repair → STL。支持 --engine、--views、--skip-generate
image-to-relief.py 浮雕/夜灯双模式，4 色量化（Bambu AMS），彩色 OBJ + STL 双输出

架构设计

设计了 4 阶段管线架构，每个阶段独立可替换：

Input Image ──→ [Stage 1: Image→3D] ──→ [Stage 2: Mesh Repair] ──→ [Stage 3: Slice] ──→ [Stage 4: Print]
                  TripoSR / Hunyuan3D       trimesh + pymeshfix          OrcaSlicer CLI       Bambu Studio

每阶段通过 JSON 传递结构化结果，包含 output、vertices、faces、 watertight、dimensions_mm 等字段。这使得阶段之间解耦，可以单独替换引擎或后处理。

经验：输出格式选择很重要

GLB 适合预览（带纹理），STL 适合打印（无纹理但所有切片软件都支持），OBJ 适合建模软件导入。 每种格式有明确的适用场景，不要在一种格式上妥协。 项目采用 生成 GLB → 修复后导出 STL 的双格式策略。

2
Hunyuan3D-2.1 集成 —— 在 6GB 显存上跑大模型
05-10

目标

引入腾讯混元 Hunyuan3D-2.1 作为第二个 AI 引擎，提供更高质量的几何生成。 该模型基于 ComfyUI 生态，需要处理便携版 Python 环境、模块路径兼容性、以及 6GB VRAM 的极限挑战。

模型分析

组件参数量VRAM (fp16)
DiT (Diffusion Transformer)~3B~6GB
Shape VAE~328M~0.66GB
Conditioner (DINO + CLIP)~304M~0.6GB
Total~3.6B~6.86GB

最大挑战：6GB VRAM 跑 6.86GB 模型

模型加载后占用 6.86GB，超出物理 VRAM 约 0.9GB。Windows 会将溢出部分分配到共享 GPU 内存（系统 RAM）， 导致推理时 PCIe 带宽成为瓶颈。实测：首次推理 67s/步，热降频后恶化到 287s/步。

应对策略：

  • 建议使用 --steps 5~10 快速预览，确认参数后再挂机长跑
  • 关闭浏览器（Chrome/Edge 占用 1-2GB VRAM 硬件加速）
  • 笔记本使用散热底座缓解 thermal throttling
  • 使用 --resolution 128 降低 Marching Cubes 开销

踩坑：ComfyUI 自定义节点的 import 地狱

ComfyUI 自定义节点目录名为 ComfyUI-Hunyuan3d-2-1（含连字符），Python 无法直接 import。 需要 monkey-patch importlib 的模块查找逻辑，在 Hunyuan3D 相关 import 时动态重写模块路径。 此外便携版的内嵌 Python 需要正确的 sys.path 设置才能找到所有依赖。

经验：对硬件约束诚实

6GB VRAM 是一个硬边界。不是"可能慢一点"的问题，而是从 30s/步 到 287s/步 的数量级差异。 在文档中诚实记录实测数据，比给用户虚假期望好得多。 hunyuan3d/engine-report.md 中记录了每个组件的精确 VRAM 占用，帮助用户判断是否适合他们的硬件。

3
Web 平台 —— 从命令行到浏览器
05-10 ~ 05-11

目标

CLI 工具功能完善但使用门槛高 —— 用户需要记住参数、手动管理文件、无法监控进度。 需要一个 Web 界面，让用户通过浏览器提交任务、实时查看日志、管理输出文件。 核心约束：不修改任何已有的 CLI 脚本。

架构决策

决策 FastAPI 异步原生支持（asyncio subprocess）、自动 OpenAPI 文档、类型安全
决策 SQLite (WAL) 零配置、并发安全、可按状态/日期查询。比 JSON 文件更适合任务管理
决策 SSE 非 WebSocket 进度推送是单向的，SSE 更简单：原生 EventSource、自动重连、无需额外依赖
决策 asyncio.Lock GPU 任务串行（一次只能跑一个），CPU 任务（浮雕、修复）并发。简单而有效
决策 子进程调用 Web 服务通过 asyncio.create_subprocess_exec() 调用 CLI 脚本，stdout 逐行推送 SSE
决策 Vanilla JS SPA 零构建工具、零 npm 依赖。Hash 路由 + 动态模板，一个 HTML 文件承载整个前端

初版 SPA

第一版前端是一个约 800 行的 templates/index.html，包含：

  • Hash-based 路由：Dashboard、New Task、Task Detail、Browse 四个页面
  • SSE 实时日志流：EventSource 接收进度，逐行渲染
  • 暗色主题：CSS 变量体系，适配长时间使用的视觉舒适度
  • GPU 任务排队：asyncio.Lock 保证同一时间只有一个 GPU 任务运行

经验：子进程优于进程内调用

最初考虑把 CLI 脚本重构为 Python 模块直接 import 调用。但子进程方案有不可替代的优势： （1）零脚本改动，CLI 和 Web 共享完全相同的代码路径； （2）进程隔离，AI 模型的内存泄漏不会影响 Web 服务； （3）可独立测试，Web 挂了 CLI 照样用。 代价是多几百毫秒的进程启动时间 —— 相比 AI 推理的几十秒到几十分钟，可以忽略不计。

工作流系统 —— 从单任务到 DAG 编排
05-11 ~ 05-12

目标

单独的 6 个 Pipeline 类型无法满足复杂需求 —— 用户想要 "文字 → AI 生图 → 背景移除 → 3D 生成 → 修复" 这样的组合流程。 需要一个可视化工作流编辑器，让用户拖拽节点、连接端口、一键运行完整链路。

关键设计

引擎 Workflow Engine 拓扑排序 → 依赖解析 → 按层并行执行。每个节点独立状态（queued/running/completed/failed），失败节点阻断下游
节点 25+ Node Types 4 大类：Input（文件/文本/参数）、Generate（TripoSR/Hunyuan3D/Text2Img/Relief）、Process（Crop/Scale/灰度/去背景/简化/平滑）、Output（STL导出/视图渲染）
前端 LiteGraph.js 成熟的 DAG 可视化库：拖拽添加节点、连线定义数据流、画布缩放平移、节点参数面板
传递 参数级联 上游节点的输出端口自动映射为下游节点的输入参数。端口与参数分离：端口定义数据流，参数定义节点行为
运行 SSE 实时驱动 Runner 页面：DAG 状态着色（绿/蓝/红/灰）+ 节点 Tab 切换查看输入输出 + 图片/STL 预览下载
内联 Inline Nodes 纯 Python 处理节点（裁切、缩放、简化等）不经过子进程，直接在引擎中同步执行，避免进程启动开销

数据流示例

┌─────────────┐     text     ┌─────────────┐    image    ┌──────────────┐    image    ┌──────────────┐
│  Text Input  │───────────→ │  Text2Image  │──────────→ │  Remove BG   │──────────→ │  TripoSR 3D  │
└─────────────┘              └─────────────┘            └──────────────┘            └──────┬───────┘
                                                                                           │ mesh
                                                                                           ▼
                                                                                  ┌──────────────┐
                                                                                  │  Mesh Repair │
                                                                                  └──────┬───────┘
                                                                                         │ stl
                                                                                         ▼
                                                                                  ┌──────────────┐
                                                                                  │  Print STL   │
                                                                                  └──────────────┘

经验：参数级联是工作流的灵魂

最初设计中，每个节点需要手动填写参数。但实际操作中，70% 的参数都是"取上游输出"。 引入参数级联后：上游输出自动出现在下游的可用参数中，用户只需确认或微调。 这大大降低了工作流的使用门槛 —— 从"配置 10 个参数"变成了"连 3 根线 + 点运行"。

经验：零构建工具的策略选择

使用原生 ES modules 而非 webpack/vite，是基于项目场景的刻意选择： （1）受众：3D 打印爱好者，不是前端开发者，不需要 npm 生态； （2）规模：~3000 行 JS，模块拆分的收益来自组织而非性能； （3）维护：零依赖意味着没有 supply chain 风险，没有版本升级 breakage。 唯一的"依赖"是通过 CDN 加载的 LiteGraph.js —— 用于工作流 DAG 可视化。

📖 经验与教训

🎯 先验证核心假设

整个项目建立在 "RTX 3060 6GB 能跑 AI 3D 生成" 这个假设上。 Phase 0 的唯���目标就是验证这一点。确认可行后才扩展到管线、Web、工作流。 如果核心假设不成立，后面的一切都是浪费。

📐 阶段间通过数据接口解耦

Pipeline 的 4 个阶段通过 JSON 交换数据（output + vertices + faces + watertight + dimensions_mm）， 而不是直接传递 Python 对象。这让每个阶段可以独立替换 —— TripoSR 换 Hunyuan3D 只改 Stage 1 的一个参数。

🧩 子进程比进程内调用更好

虽然多了几百毫秒的启动开销，但获得了进程隔离、零脚本改动、独立可测试、崩溃不影响主服务等关键优势。 对于动辄几十秒到几十分钟的 AI 推理任务，启动开销完全可以忽略。

🎨 零构建工具有它的位置

不是说 webpack/vite 不好，而是说在特定场景（非前端团队、中等规模、追求零维护）下， Vanilla ES modules 是更好的选择。没有依赖就意味着没有 breaking change、没有 security advisory、没有升级 chore。

📝 对硬件约束诚实

Hunyuan3D-2.1 在 6GB 显卡上的实测数据（6.86GB 加载、67-287s/步、热降频恶化）全部公开记录。 用户有权利知道在他们的硬件上会发生什么。诚实比美化更能建立信任。

🔧 i18n 要从第一天就做对

初版中 lang==='zh'?'加载中':'Loading...' 的写法在只有几个字符串时无所谓， 但到 130 个 key 时就完全失控了。重构到 JSON locale 花了半天 —— 如果一开始就做对，只需要半小时。

📦 单体文件的生命周期

3689 行的单文件 SPA 在项目初期是合理的 —— 快速迭代、没有模块间 import 的认知开销、一个文件看清所有逻辑。 但当它从 800 行增长到 3689 行时，拆分就是必要的。关键是在"太早拆分"和"太晚拆分"之间找到平衡点。

🤖 AI 编程助手的正确用法

整个项目由 Claude Code 辅助完成。不是"AI 写代码我审查"，而是"我设计架构，AI 实现细节"。 AI 擅长：大量重复性代码（26 个路由处理函数）、模板化内容（8 个页面模块的结构）、文档生成（6 份技术文档）。 人擅长：架构决策、技术选型、边界条件的判断。各司其职。
